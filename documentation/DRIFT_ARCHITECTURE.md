## Overview

The project uses Drift as its primary local SQLite persistence layer.
The recommended flow is: Screen (BLoC/Cubit) -> Interface -> Repository -> Drift DAO -> Database.

There are two main databases:

- `AppDatabase` for business data (customers, products, categories, company details, invoices, and items).
- `SystemDatabase` for system data (users, logs, and settings).

## File Structure

```text
lib/data/database/
├── app_database.dart              # Main database, schema, and migrations
├── app_database.g.dart            # Generated by Drift
├── system_database.dart           # System database
├── system_database.g.dart         # Generated by Drift
├── dao/                           # DAOs (XxxDao)
├── table/                         # Drift tables (XxxRecords)
│   └── system/                    # System database tables
├── extension/                     # Conversions to Companions
└── mapper/                        # XxxRecord -> domain conversions
```

## Layer Flow

```text
Screen (BLoC/Cubit)
  -> Interface (lib/core/interface/)
  -> Repository (lib/domain/repository/)
  -> DAO (lib/data/database/dao/)
  -> Tables/AppDatabase/SystemDatabase
  -> SQLite
```

## Architecture Standards

### Repository + DAO

- The UI depends on interfaces in `lib/core/interface/`.
- Repositories in `lib/domain/repository/` coordinate DAOs and business rules.
- DAOs in `lib/data/database/dao/` perform persistence operations and queries.
- Transactions involving multiple entities belong in the repository, not the DAO.

### Domain Separation

- Domain models in `lib/core/models/` do not depend on Drift.
- Generated records (`XxxRecord`) represent the physical schema.
- Conversion between domain and persistence is handled by `mapper/` and `extension/`.
- Do not use `@UseRowClass` with domain entities.

### Error Handling

- Repositories catch exceptions internally and return `ResultStatus.error(...)`.
- The presentation layer does not wrap repository calls in `try/catch`.

## Schema Versioning

Current database state:

- `AppDatabase`: `schemaVersion => 12`
- `SystemDatabase`: `schemaVersion => 1`

When changing tables, DAOs, or persisted types:

1. Update the schema in the correct database.
2. Implement/update the migration strategy.
3. Generate code with `dart run build_runner build`.
4. Validate with `dart analyze` and `flutter test`.

## Best Practices

- Keep migrations small, explicit, and incremental.
- Centralize business logic in the repository.
- Avoid exposing persistence details to higher layers.
- Use consistent names: table `XxxRecords`, row `XxxRecord`, DAO `XxxDao`.
- Preserve data when applicable; before production, breaking changes may be accepted when agreed upon by the team.
